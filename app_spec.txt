<project_specification mode="greenfield">
  <project_name>Elicta — Live Requirements Elicitation Assistant</project_name>

  <overview>
    A desktop assistant that listens to a live client requirements meeting, detects
    ambiguity in the moment, and surfaces one short follow-up question the operator
    can ask before the client moves on. The load-bearing idea is that the expensive
    analyst reasoning happens before the meeting: an offline pass compiles a bank of
    pre-reasoned candidate questions, so the live path is retrieval and selection in
    tens of milliseconds rather than inference in seconds. After the meeting it
    becomes a conversational interface that produces BMAD planning artifacts in
    which every claim is traceable to a timestamped utterance.
  </overview>

  <target_audience>
    Primary — the operator: the PM or business analyst running a client requirements
    meeting from a second machine. They glance at the panel, tap it, and never type
    during the meeting. Secondary — the reviewer: a delivery lead or architect who
    receives the artifacts and needs to see what the client actually said as opposed
    to what the system inferred.
  </target_audience>

  <technology_stack>
    <shared_core>
      <language>Rust (no garbage collector, safe on the real-time audio thread)</language>
      <matching>aho-corasick for lexicon scanning</matching>
      <bindings>UniFFI for Swift and Kotlin; C ABI elsewhere</bindings>
      <storage>SQLite with sqlite-vec for the on-device question bank</storage>
    </shared_core>
    <frontend>
      <framework>Tauri 2 shell with a system-webview panel</framework>
      <language>TypeScript</language>
      <styling>Tailwind CSS</styling>
      <state_management>Tauri IPC events into a small reactive store</state_management>
    </frontend>
    <backend>
      <framework>Python 3.12 with FastAPI (service tier)</framework>
      <agent_runtime>Claude Agent SDK (claude-agent-sdk) for the compiler and debrief agents</agent_runtime>
      <single_shot>Claude Messages API for the slow lane, with a hand-partitioned cache prefix</single_shot>
      <orm>SQLAlchemy 2.0 (async)</orm>
      <validation>Pydantic v2</validation>
    </backend>
    <database>
      <primary>PostgreSQL (service tier)</primary>
      <edge>SQLite with sqlite-vec on the operator device (question bank, session state)</edge>
    </database>
    <communication>
      <api_style>REST over TLS, plus server-sent events for second-screen sync</api_style>
      <response_format>JSON envelope: { "data": ..., "error": null, "status": 200 }</response_format>
    </communication>
    <external_processors>
      <capture>Managed per-participant meeting capture vendor (unselected, PRD decision D4)</capture>
      <asr_live>Streaming ASR with per-word confidence and per-token language tags</asr_live>
      <asr_record>Two independent batch ASR engines, reconciled</asr_record>
      <inference>Claude API (Messages API and Agent SDK)</inference>
    </external_processors>
  </technology_stack>

  <prerequisites>
    - Rust 1.79+ with cargo and the Tauri 2 CLI
    - Python 3.12+ with uv installed
    - Node.js 20+ with pnpm for the desktop shell
    - PostgreSQL 16 for the service tier; SQLite bundled on device
    - API keys: ANTHROPIC_API_KEY, live ASR vendor key, record-path vendor keys, managed capture vendor key
    - Environment variables documented in .env.example: DATABASE_URL, ANTHROPIC_API_KEY, ASR_LIVE_KEY, ASR_RECORD_A_KEY, ASR_RECORD_B_KEY, CAPTURE_VENDOR_KEY, EGRESS_LOG_PATH, DATA_REGION
    - Legal sign-off on PRD items L1 to L5 before the capture layer ships
  </prerequisites>

        - Top: capture state indicator and detected-language chips
        - Centre: one nudge — 3 to 5 word stub in large type, full question beneath at
          smaller weight, trigger reason in the operator language at smallest weight
        - Below: dimmed history of prior nudges
        - Bottom: coverage indicator (sections filled over total, time remaining) and the

        - De-emphasised text input as the escape hatch

      CJK stack:   Inter, Noto Sans SC, Noto Sans TC, sans-serif
    </typography>
    <animations>
      Nudge entry: instant — no typing animation, no streaming, no fade longer than 120ms
      Chip tap:    80ms scale feedback, state change is immediate and local
      Coverage:    200ms ease on fill-state change
      Rationale:   every animation competes with the client for the operator's attention,
                   so the live panel is deliberately the least animated surface in the product
    </animations>

  <key_interactions>
    <interaction number="1" name="Prepare an engagement and compile the bank">
      1. User creates an engagement with client, sector, purpose, target template
      2. User uploads reference documents, tagging each ground_truth, hypothesis, or superseded
      3. User adds client vocabulary terms for keyterm prompting
      4. System runs the Analyst pass and emits 150 to 300 candidates
      5. User reviews the question tree, prunes weak candidates, reorders priorities
    </interaction>
    <interaction number="2" name="Set up a meeting in under two minutes">
      1. User creates a meeting under the engagement
      2. System pre-populates attendees from the calendar invite
      3. User confirms attendee roles and decision authority
      4. User states the session purpose and picks target template sections
      5. System displays the inherited open-questions list for review
    </interaction>
    <interaction number="3" name="Surface a nudge inside the conversational window">
      1. Client says a requirement containing an unquantified adjective
      2. System detects the span by lexicon match on the frozen partial
      3. System suppresses the nudge if the span confidence or language tag confidence is low
      4. System retrieves and ranks candidates, instantiating the winner by slot interpolation
      5. Panel displays one nudge with its trigger reason, complete, in a single render
      6. User taps Asked it, which marks the coverage slot satisfied locally
    </interaction>
    <interaction number="4" name="Debrief and produce artifacts">
      1. System runs dual-engine batch transcription over the retained audio
      2. System reconciles the two outputs and flags divergent spans
      3. System discards the raw audio once diarization completes
      4. System generates the coverage matrix, open questions, brief, follow-up email
      5. User reviews flagged divergences and confirms or corrects each
      6. System merges requirements_state forward into the next meeting
    </interaction>
